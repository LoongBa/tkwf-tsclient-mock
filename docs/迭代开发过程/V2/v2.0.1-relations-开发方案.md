## 一、背景与目标

### 1.1 现状

v2.0.0 已实现策略化数据生成（`_strategy`/`_generators`/`_faker`），但工厂生成的数据是孤立的——`defineMerchant.makeN(5)` 只生成 5 个 merchant，不生成关联的 paymentLog，也不会自动设置 `merchantId`/`logIds` 外键。

### 1.2 目标

1. **`_relations` 配置**：声明关联工厂与数量，生成时自动创建关联数据
2. **循环防护**：A→B→A 配置时自动检测并终止（visited-set + 深度上限）
3. **FK 自动关联**：复用 `inferDtoRelations` 的 `fkField` 推断，自动设置外键
4. **向后兼容**：不传 `_relations` 时行为与 v2.0.0 完全一致

### 1.3 不做什么

- ❌ 不做跨工厂 `_relations` 的 `inverse` 双向同步（已有 `registerRelation.inverse` 做运行时同步，`_relations` 只做生成时的 FK 设置）
- ❌ 不做 `_relations` 的 `traits`/`withComments` 变体（留后续版本）

## 三、方案设计

### 3.0 设计决策

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 循环防护 | **visited-set + 深度上限（默认 3）**——检测到已访问的工厂名时跳过 |
| 2 | FK 字段名 | **复用 `inferDtoRelations` 的 `fkField` 推断**（如 `merchantId`） |
| 3 | 生成时机 | **`makeN()` 内部递归生成**——主实体生成后立即展开关联 |
| 4 | 返回形态 | **`makeN()` 只返回主实体数组**，关联数据写入 `_relations` 中指定的 `targetFactory` 的 `db`（或 `MockDb` 实例） |

### 3.1 `_relations` 配置

```typescript
export interface RelationFactoryConfig {
  /** 目标工厂 */
  factory: MockFactory<unknown>;
  /** 每主实体生成的关联数量 */
  count: number;
  /** 外键字段名（可选，默认从 inferDtoRelations 推断） */
  fkField?: string;
  /** 关联字段名（可选，默认根据 factory 类型推断） */
  targetField?: string;
}

// MockFactoryOptions 新增
_relations?: Record<string, RelationFactoryConfig>;
```

### 3.2 生成逻辑

```typescript
function generateRelations(
  parentId: string | number,
  relations: Record<string, RelationFactoryConfig>,
  visited: Set<string>,
  depth: number,
  ctx: GeneratorContext,
): void {
  if (depth > MAX_RELATION_DEPTH) return;

  for (const [field, config] of Object.entries(relations)) {
    const factoryKey = config.factory.constructor?.name ?? field;
    if (visited.has(factoryKey)) continue;
    visited.add(factoryKey);

    const children = config.factory.makeN(config.count, {} as never);
    // 关联数据写入 factory 的 db（或返回给调用方）
    // FK 字段由 inferDtoRelations 推断或 config.fkField 指定
  }
}
```
