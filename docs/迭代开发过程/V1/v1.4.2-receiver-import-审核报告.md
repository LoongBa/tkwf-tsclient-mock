## 代码质量评估

### mock-db.ts buildDataset 增强（+15 行）

**优点**：
- 检测逻辑独立前置，不干扰原有导入循环——职责清晰，改动面最小
- 守卫条件 `mode !== "ignore" && declaredTables.size > 0` 两个条件都必要：前者保持向后兼容，后者避免空初始化误报
- 错误/警告信息包含双向信息（未知表 + 已声明表），接收方可直接对照排查
- 测试用 `try/finally` 恢复 `console.warn` spy，无测试间污染

**问题**：无阻断性/主要问题。

**观察（不阻塞）**：
- 与 `strict` FK 校验正交：`unknownTables` 管"表存在性"，`strict` 管"行引用完整性"，两者可组合使用
- `importDatasetSeed` 内部调用 `buildDataset`（无 unknownTables 参数透传）——Node 端如需检测需自行调用 buildDataset；文档已通过 Step 5a 示例覆盖（parseDatasetSeed + buildDataset），可接受

### mock-db.test.ts（+4 用例，74 用例/文件）

**覆盖**：
- warn 输出（含未知表名 + 已声明表名）
- error 抛错
- ignore 默认静默 + 数据正常导入（向后兼容）
- 空初始化 db 不检测（守卫条件）

**缺口**：audit 确认 importDatasetSeed 路径未透传 unknownTables——已知设计取舍，文档已规避（推荐 parseDatasetSeed + buildDataset 组合），非阻塞。

## 建议

1. **（可选）`importDatasetSeed` 增加 unknownTables 透传**：Node 接收方直接用 `importDatasetSeed(db, path, { unknownTables: "error" })`（CI 立即失败）。当前需先 `parseDatasetSeed` + `buildDataset` 两步才能检测，Node 路径略绕。
2. **（后续）跨项目共享场景的 HTTP 状态语义验证**：§4.8 说明"单 Transport 共享状态"，可后续补一个多客户端并发 mutation 可见性的示例测试。
