## 一、背景与目标

### 1.1 现状

v1.2.0（场景切换）已可用：
- `MockTransport`：field 分发 + 场景注入（`setScenario`/`ctx.scenario`）
- `createMockDb`：多命名数据集 + 内存查询语义
- `createScenarioContext`：db 数据集 + transport 注入联动切换
- `configureSidecar`：可插拔存储注入模式（`SidecarStore` 接口）

**缺口**：
1. mock 数据是**手工/Agent 填充**的——无法直接复用真实后端的请求/响应
2. 集成测试需要**真实数据链路的确定性回放**，当前无此能力
3. 后端真实响应中有**非确定性字段**（时间戳/UUID/自增 ID），直接录制回放会对不上

### 1.2 目标

1. **录制（record）**：拦截 Transport 请求/响应 → 序列化存储（内存默认 + 文件可选）
2. **回放（replay）**：从录制数据匹配请求 → 返回录制响应（确定性、不依赖后端）
3. **非确定性归一化**：时间戳/UUID/自增 ID 等字段自动归一化，回放可重复
4. **可插拔存储**：复用 `configureSidecar` 注入模式——`RecordingStore` 接口 + `configureRecordingStore`
5. **三态模式**：`record`（录制）/ `replay`（回放）/ `passthrough`（直通不录）——复刻 Polly.js 模式
6. **兼容双入口**：`execute()` 与 `executeRawGraphQL()` 都能录制/回放

### 1.3 不做什么

- ❌ 不实现完整 HAR 1.2 格式（Transport 层无 HTTP 语义，HAR 的 timings/cookies/headersSize 无用）——用轻量自定义 JSON
- ❌ 不做 HTTP 层录制（MSW/Polly 式网络拦截）——只做 Transport 接口层录制
- ❌ 不内置文件系统依赖到核心（`node:fs` 仅放可选 FileRecordingStore，默认内存存储）
- ❌ 不改 `MockTransport.execute()` 核心流程、不改 `Transport` 接口、不改主包 `@tkwf/tsclient`
- ❌ 不做自动噪声检测（Keploy 式启发式）——用录制时替换 + 用户归一化函数（L2+L4 混合）

## 三、方案设计

### 3.0 设计决策（已确认）

| # | 决策点 | 推荐方案 | 备选 |

| # | 决策点 | 结论 |

### 3.1 录制模型

```typescript
/** 单个录制条目（一次 execute/executeRawGraphQL 的请求→响应对） */
export interface RecordedEntry {
  field: string;                 // handler field 名
  type: "query" | "mutation";
  variables?: Record<string, unknown>;  // 归一化后的请求 variables
  result?: unknown;              // 成功响应的 data
  error?: {
    message: string;
    source?: "injected" | "failRate" | "timeout" | "missingHandler" | "handler" | "transport" | "network";
    errorCode?: string;          // DomainClientError 携带的 errCode（可选，🟡1）
  };
  durationMs: number;
  timestamp: string;             // ISO-8601（录制时生成，回放不用于匹配）
}

/** 一次命名录制会话 */
export interface Recording {
  name: string;                  // 录制会话名
  scenario?: string;             // 录制时的场景名（可选）
  entries: RecordedEntry[];
  createdAt: string;
  version: string;               // mock 包版本（兼容性检测）
}
```

**匹配键**：`field + type + 归一化 variables`（variables 键排序、`undefined`→`{}` 归一化）。

### 3.2 RecordingStore（可插拔存储）

```typescript
export interface RecordingStore {
  start(name: string, options?: { scenario?: string }): void | Promise<void>;   // 开始录制会话
  record(entry: RecordedEntry): void | Promise<void>;                          // 记录单条（仅模式=record 时）
  stop(): Recording | undefined | Promise<Recording | undefined>;              // 结束会话，返回录制
  load(name: string): Recording | undefined | Promise<Recording | undefined>;  // 加载录制（回放用）
  list(): string[] | Promise<string[]>;                                        // 列出可用录制名
}

// 默认内存实现 + 注入模式（复用 configureSidecar）
const memoryStore: RecordingStore = { ... };
let activeStore: RecordingStore = memoryStore;
export function configureRecordingStore(store: RecordingStore): void { activeStore = store; }
```

**异步兼容（Oracle 审查 🔴1）**：所有方法返回类型允许 `Promise`——对齐 `SidecarStore` 的混合 sync/async 模式，使 IndexedDB 等浏览器异步后端可实现。`FileRecordingStore` 用同步 `node:fs` 返回非 Promise 值仍合法（`void` 是 `Promise<void>` 的兼容子集）。

**生命周期约束（Oracle 审查 🟡5）**：
- `record()` 必须在 `start()` 之后、`stop()` 之前调用，否则抛错
- `stop()` 在 `start()` 之前调用 → 抛错或返回 undefined（实现二选一，默认抛错）
- 同一 store 未 `stop()` 时再次 `start()` → 抛错（防止覆盖进行中的会话）
- `load()`/`list()` 可在 `start()` 进行中调用（读取已完成的录制，不影响当前会话）

**兼容性**：与 `configureSidecar` 完全同构——消费端可注入 `FileRecordingStore`（node:fs）或 IndexedDB 等。

### 3.3 createRecordingTransport（装饰器）

```typescript
export type RecordingMode = "record" | "replay" | "passthrough";

export interface RecordingTransportOptions {
  mode: RecordingMode;                    // 三态模式
  recordingName: string;                  // 录制会话名
  store?: RecordingStore;                 // 可选，默认 activeStore
  normalizers?: {
    normalizeVariables?: (variables: Record<string, unknown> | undefined, field: string) => Record<string, unknown> | undefined;
    normalizeResult?: (result: unknown, field: string) => unknown;
  };
  order?: boolean;                        // false = 无序匹配（polling 场景），默认 true = 有序 FIFO
  maxUsageCount?: number;                 // 单条可消费次数，默认 1
  onMiss?: (op: { field: string; type: string; variables?: unknown }) => void;  // 回放未命中回调
  strictVersion?: boolean;                // true = 录制版本不匹配抛错；默认 false = 仅 console.warn（🟡6）
  signal?: AbortSignal;                   // 可选：回放时检查该 signal 是否已 aborted
}

export function createRecordingTransport(
  transport: Transport,
  options: RecordingTransportOptions,
): Transport;
```

**实现要点（装饰器包装，不侵入 MockTransport）**——`execute` 与 `executeRawGraphQL` **双入口完整处理**（Oracle 审查 🔴2）：

```
execute(op):
  switch (mode):
    case "replay":
      1. 查 activeStore.load(recordingName) → recordings（含 version 检查：不匹配按 strictVersion 决定 warn/throw）
      2. 匹配：找第一条 field+type+variables 匹配的条目
           order=true  → 按录制序 FIFO 取第一个仍有剩余 maxUsageCount 的条目
           order=false → 取第一个（按录制序）仍有剩余 maxUsageCount 的条目（确定性，非随机，🟡3）
      3. 命中 → 若 error 则 throw MockRecordingError，否则 return result（消费 maxUsageCount 次）
      4. 未命中 / 该 key 所有条目耗尽 → onMiss() 回调 + throw Error("Mock: no recorded response for <field>")
    case "record":
      1. try { result = await transport.execute(op); record({field,type,variables: normalizeVariables(v),result: normalizeResult(result)}); return result }
      2. catch (e) { record({field,type,variables,error: {message, source, errorCode}}); throw e }
    case "passthrough":
      return transport.execute(op)   // 直通不录

executeRawGraphQL(query, sessionKey?, signal?):
  switch (mode):
    case "replay":
      1. extractField(query) 提取 field 名（复用 MockTransport 的 extractField 逻辑）
      2. 按 (field, type: "query", variables: undefined→{}) 匹配 → 命中返回 result / 未命中 onMiss+throw
      3. 局限：raw query 无法可靠提取 mutation 类型 → 录制 executeRawGraphQL 的 mutation 不受支持（文档标注）
    case "record":
      try { result = await transport.executeRawGraphQL(query, sessionKey, signal); record({field: extractField(query), type: "query", result}); return result }
      catch (e) { record({field, error}); throw e }
    case "passthrough":
      return transport.executeRawGraphQL(query, sessionKey, signal)
```

**回放错误包装（Oracle 审查 🟡4）**：

```typescript
export class MockRecordingError extends Error {
  source: string;                // 录制时的错误来源
  originalMessage: string;       // 原始错误 message
  errorCode?: string;            // DomainClientError 的 errCode（可选）
}
```

**归一化时机**：
- `normalizeVariables` 在**录制和回放**都运行（保证匹配一致）——用户函数之后，系统再做键排序 + `undefined`→`{}` 归一化（两步流程）
- `normalizeResult` 在**录制时**运行（存储的就是归一化后的确定性数据）

### 3.4 内置归一化器

```typescript
/** 默认归一化：时间戳/UUID 替换为确定性占位符（录制时运行，回放不运行） */
export function normalizeTimestamps(value: unknown, replaceWith = "2026-01-01T00:00:00.000Z"): unknown;
export function normalizeUuids(value: unknown, replaceWith = "00000000-0000-0000-0000-000000000000"): unknown;
```

- 递归遍历对象/数组
- `normalizeTimestamps`：匹配 ISO-8601 字符串 → 替换为固定时间戳
- `normalizeUuids`：匹配 UUID v1-v5 → 替换为固定 UUID
- **ID 保留**：自增 ID 不归一化（关联性重要，对应 Servirtium `normalize` vs `redact` 的取舍——ID 用 normalize 保持关联，纯噪声用 redact）
- **使用指南（Oracle 审查 🟡2）**：`normalizeTimestamps`/`normalizeUuids` **默认仅用于 `normalizeResult`**——避免误伤 variables 中的合法业务 ID/时间戳（如 `{ accountId: "550e..." }` 是真实 UUID 而非噪声）。若 variables 侧确需去噪，应写自定义 `normalizeVariables` 指定具体字段路径。

### 3.5 FileRecordingStore（可选）

```typescript
/**
 * 基于 node:fs 的文件存储（独立模块，不污染核心）。
 * 目录结构：<dir>/<recordingName>.json，每个文件一个 Recording。
 */
export class FileRecordingStore implements RecordingStore {
  constructor(dir: string);   // 录制文件目录
  start(name, options?): void;
  record(entry): void;
  stop(): Recording | undefined;
  load(name): Recording | undefined;   // 从 <dir>/<name>.json 读取
  list(): string[];                    // 列出 <dir>/*.json 文件名
}
```

- 使用 `node:fs/promises`（异步）或同步 `node:fs`——**决策**：用同步 `node:fs`（录制过程简单），或注入异步 store。**推荐**：`RecordingStore` 方法全同步（简单），`FileRecordingStore` 内部用同步 `node:fs`。

### 3.6 与场景（scenario）集成

- 可选：`createRecordingTransport` 的 `recordingName` 可含场景名（`paymentLogs-error`）——消费端自行约定
- replay 模式返回的响应**不经过** scenario 注入（录制的是最终 result，已含当时场景效果）
- **不**把 record/replay 做成 `setScenario("record")` 扩展——保持两者正交，避免侵入 scenario 模型
