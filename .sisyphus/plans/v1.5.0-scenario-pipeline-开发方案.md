## 一、背景与目标

### 1.1 现状

v1.4.0 的 MockDataSpec 已支持 `scenarios` 字段（`Record<场景名, Record<实体名, { count }>>`），但存在两个缺陷（项目组反馈评估确认）：

| # | 缺陷 | 证据 | 影响 |
|---|------|------|------|
| 1 | **scenarios 定义了但 generateFromSpec 不消费**（堵点⑤） | `validateScenarios`（mock-data-spec.ts:128-143）只校验结构；`generateFromSpec` 管线（:237-241）用 `entity.count` 硬编码，从不读取 `spec.scenarios` | Agent 按 SKILL.md 填写 scenarios 后生成结果不变，文档误导 |
| 2 | **computed 在 relations 之前执行**（Bug②） | 管线：`makeN → applyPostPass(computed+nullable) → applyRelations → collectIds`（:237-241） | computed 字段无法引用 belongsTo 关系填充的 FK 字段（求值时 FK 尚未写入），`coalesce(fkField, ...)` 永远取不到 FK 值 |

### 1.2 目标

1. **场景化生成**：`generateFromSpec(spec, { scenario: "minimal" })` 按场景覆盖实体 count，未提及实体保持默认 count；未知场景抛描述性错误
2. **computed 管线修正**：管线调整为 `makeN → applyRelations → applyComputed → applyNullable → collectIds`，computed 可引用 relation 填充的 FK 字段
3. **parse 校验增强**：`validateScenarios` 增加"场景引用的实体必须存在"校验，提前捕获拼写错误
4. **文档同步**：SKILL.md / MOCK_SPEC.md.template / example.json / README 的 scenarios 说明从"仅供人类阅读"升级为"受支持用法"，并移除此前标注的 ⚠️ 警告

### 1.3 不做什么

- ❌ 不做 `scenarios` 的运行时联动（`createScenarioContext` 仍是运行时场景切换的唯一入口；`generateFromSpec` 场景参数只影响**生成时**数量）
- ❌ 不做 computed 引用**父实体**字段（computed 只能引用**同记录**字段；跨实体取值由 relations 的 `targetField` 在父侧池中完成）
- ❌ 不做 computed 链式依赖排序（computed 仍按字段声明顺序求值，依赖项需先声明）
- ❌ 不做 `empty` 场景的警告抑制（父实体 count=0 时子实体 relation 池为空 → 保留现有 warn，信息准确）
- ❌ 不修改 `createScenarioContext` / `createMockDb` 现有行为

## 二、功能设计

### 2.1 `GenerateFromSpecOptions` 增加 `scenario` 参数

**修改文件**：`src/mock-data-spec.ts`

```typescript
export interface GenerateFromSpecOptions {
  /** 外部注入的 faker 实例（结构：faker[module][method]） */
  faker?: Record<string, unknown>;
  /** 实体名 → MockFieldSchema 记录（交由工厂做类型驱动兜底生成） */
  schemas?: Record<string, Record<string, unknown>>;
  /** 场景名：覆盖 spec.scenarios[scenario] 中声明的实体 count（v1.5.0 新增） */
  scenario?: string;
}
```

**实现逻辑**（`generateFromSpec` 内，位于拓扑排序之后、逐实体生成之前）：

```typescript
// 解析场景覆盖：scenario → 实体名 → count
function resolveScenarioCounts(
  spec: MockDataSpec,
  scenarioName: string | undefined,
): Map<string, number> {
  const counts = new Map<string, number>();
  for (const [name, entity] of Object.entries(spec.entities)) {
    counts.set(name, entity.count);
  }
  if (scenarioName === undefined) return counts;
  const scenario = spec.scenarios?.[scenarioName];
  if (scenario === undefined) {
    const available = Object.keys(spec.scenarios ?? {}).join(", ");
    throw new Error(
      `[tsclient-mock] generateFromSpec: 未知场景 "${scenarioName}"。`
      + (available.length > 0 ? ` 可用场景：${available}。` : " 该 spec 未定义任何场景。"),
    );
  }
  for (const [entityName, def] of Object.entries(scenario)) {
    counts.set(entityName, def.count);  // 已由 parse 校验保证 entityName 存在
  }
  return counts;
}
```

**生成循环改动**：

```typescript
const entityCounts = resolveScenarioCounts(spec, options?.scenario);
for (let index = 0; index < order.length; index++) {
  const entityName = order[index];
  const entity = spec.entities[entityName];
  const count = entityCounts.get(entityName) ?? entity.count;
  // ...
  const items = factory.makeN(count) as Record<string, unknown>[];
  // ...
}
```

**边界语义**：
- 场景未提及的实体 → 保持 `spec.entities[name].count`（部分覆盖）
- count=0 → `makeN(0)` 返回 `[]`，无 id 入池；依赖它的子实体 relation 触发现有"数据池为空"warn 并跳过 FK 填充
- 场景对象中实体的声明顺序无关（counts map 键查找）
- 确定性保持：实体生成顺序、seed 计算（`seed + index + 1`）均不变，仅 count 变化

### 2.2 computed 管线顺序修正

**当前管线**（mock-data-spec.ts:237-241）：

```
makeN → applyPostPass（computed + nullable）→ applyRelations（belongsTo FK）→ collectIds
```

**新管线**：

```
makeN → applyRelations → applyComputed → applyNullable → collectIds
```

**改动**：

1. 将 `applyPostPass` 拆分为两个函数：
   - `applyComputed(entityName, entity, items)`：仅 computed 求值（原 :592-598 循环）
   - `applyNullable(entityName, entity, items)`：仅 nullable 权重置空（原 :599-606 循环）
2. 管线顺序调整（:237-241）：

```typescript
const items = factory.makeN(count) as Record<string, unknown>[];
applyRelations(entityName, entity, items, idPool);   // ① FK 填充（先）
applyComputed(entityName, entity, items);            // ② computed（可引用 FK 字段）
applyNullable(entityName, entity, items);            // ③ nullable（最后，computed 结果与 FK 字段均可置空）
collectIds(entityName, items, idPool);               // ④ 池收集（含 computed 结果）
```

**语义变化与理由**：

| 场景 | 旧行为 | 新行为 | 说明 |
|------|--------|--------|------|
| computed 引用 relation FK 字段 | 取到 undefined（FK 未写入） | 取到真实 FK 值 | **本版本核心修复**（Bug②） |
| nullable 字段同时被 relation 填充 | 先置 null 后被 relation 覆盖 → 永不 null | relation 先填充 → nullable 置 null 生效 | 副作用修复（原行为是 bug） |
| nullable 字段被 computed 引用 | computed 先于 nullable → 引用原始值 | 保持（nullable 仍在 computed 后） | 行为不变 |
| 子实体 relation 引用父实体 computed 字段 | computed 先于 collectIds → 值入池 | 保持（computed 仍在 collectIds 前） | 行为不变 |

**对现有测试的影响**：现有测试无"nullable 字段同时被 relation 填充"或"computed 引用 FK 字段"的用例，268 个测试预期全部通过（实现后跑全量验证）。

### 2.3 parse 校验增强（validateScenarios）

**当前**：`validateScenarios(spec.scenarios)` 仅校验结构（对象、count 非负数字），不校验实体名存在性。

**改动**：传入实体名集合，场景中引用的实体名必须存在于 `spec.entities`：

```typescript
function validateScenarios(scenariosRaw: unknown, entityNames: Set<string>): void {
  // ... 现有结构校验不变 ...
  for (const [entityName, countRaw] of Object.entries(defRaw)) {
    if (!entityNames.has(entityName)) {
      throw new Error(
        `[tsclient-mock] parseMockDataSpec: 场景 "${scenarioName}" 引用了未定义的实体 "${entityName}"。`,
      );
    }
    // ... 现有 count 校验不变 ...
  }
}
```

**调用点**：`parseMockDataSpec` 内 `validateScenarios(spec.scenarios, new Set(Object.keys(entities)))`（:123）。

**理由**：生成期（`resolveScenarioCounts`）依赖场景实体名存在；提前到 parse 期校验可让错误在编写/加载阶段暴露，而非生成阶段。

| 风险 | 对策 |
|------|------|
| 管线顺序调整破坏现有生成的确定性输出 | 仅调整 computed/nullable 与 relations 的相对顺序；无冲突用例；全量回归 + 新增用例 6/7 锁定新语义 |
